# 页面探索正确性

讨论或改动页面探索、OpenCode 结构化输出、定位器校验或页面档案复用时阅读。本文记录当前卡住的事实和必须回答的问题，不规定实现方案。

正式用例形状（`case.json` 的 Action IR、用例编辑器、基础检查、代码生成）在 #18 之后视为冻结。探索重构应改「事实从哪来、怎么验收」，不改已发布测试计划的编辑与生成路径。

## 用户看见什么

AI 导入探索可以显示成功，任务页也能打开「定位和填写值」，但选择器经常找错控件：把 Excel **数据**（要填、要选的值）写成了定位文本，而不是 **目标**（字段名、按钮名）。

西芒杜真实导入中的对照：

| 动作 | Excel 目标（应找到谁） | Excel 数据 | 探索给出的选择器 |
| --- | --- | --- | --- |
| 填写 | 取样人 | TEST | `getByText('TEST')` |
| 选择 | 成品堆场 | 粗矿堆 | `getByRole('option', { name: '粗矿堆' })` |
| 填写 | 取样名称 | 自动测试2 | `getByLabel('请输入')` |
| 选择 | 取样类别 | 原矿开采 | `getByRole('option', { name: '原矿开采' })` |
| 选择 | 要求取样时间的起始时间 | 日期 | `getByText('2026-08-28')` |

手工在任务页改选择器可以救急，但不能当质量策略。规则仍是：发布用定位器必须来自该次探索的已验证结果，编译不得按目标文本猜。

Excel 日期格变成序列号（如 `46262`）是解析问题，不是探索模块问题。

## 当前链路实际做什么

规格把职责分成两边，当前实现也按这个分，但后半段几乎不验对错。

1. **OpenCode + Playwright MCP**  
   打开真实页面，按用例步骤操作，最后吐一个 JSON 候选：`kind`、`locators`、`pageUrl`。提示词要求「定位器必须来自真实页面观察，不要凭目标文本猜测」。
2. **宿主收结果**  
   `assignLocatorsByOrder` 把定位器对到意图步骤；`isVerifiedLocator` 只检查是不是语义模式（role/text/label 等）且文本、selector 非空。不检查定位文本是不是 Excel 目标，也不检查是不是误用了填写值。
3. **写入页面档案**  
   按 `动作:目标` 做成页面目标键，例如 `填写:取样人`。键是对的，里面的定位器可以是错的。整页压成一个默认页面状态。
4. **后续用例复用**  
   `archiveCoversSteps` 只问「这些键在不在」。在就不再开浏览器，宿主直接把档案定位器贴回新步骤。OpenCode 不参与复用。
5. **编译发布**  
   意图步骤加探索定位器变成 Action IR。编译不猜定位器。错定位器会原样进正式用例。

因此会出现：TC-001 复用旧的 `/web/IMQM14` 档案，把 `getByText('TEST')` 带进新任务；TC-002 是同一次导入里真正探索成功的，同类错误仍在。问题不在复用独有，探索本身就会产出这种定位器。

相关入口：`server/src/services/import/opencode-runner.ts`、`verified-locator.ts`、`import-review.ts`、`shared/page-archive.ts`、`intent-compile.ts`。

## 为什么要重构

改提示词或对单条点「重试」解决不了，原因有四条。

1. **提示词在鼓励错误观察。**  
   「不要凭目标文本猜测」会被理解成：先填 TEST，再按屏幕上看到的字定位。正确合同应是：按 **目标** 找到控件，**数据** 只用于填写、选择或断言。
2. **宿主没有合同。**  
   只要像语义定位器就会收下并写入档案。填写值、占位符「请输入」、下拉选项都可以过门。
3. **档案会放大一次错误。**  
   「覆盖」只看键。错事实成为该页的可复用知识，直到有人刷新或删除档案。
4. **领域里的页面状态没有落地。**  
   弹窗、下拉展开、树、表格在领域上可以是不同页面状态。实现里几乎都是 `default`。打开下拉后的 `option`、占位符、日历格子容易被当成字段本身。

长步骤超时（弹窗 + 树 + 表格，默认 `agent.timeoutMs` 180 秒）会让真实闭环失败，但是另一件事：超时是没探完，当前更严重的是探完了却是错的。

#17 的真实验收仍要求弹窗填写保存、树形选择、动态表格和主表成功提示。这条卡住的是探索正确性，不是任务页编辑器。

## 正确性缺口

重构需要先把合同和验收门说清楚，再改 OpenCode 输出或档案结构。

### 定位器合同

每种业务动作，什么才算对准了 Excel 目标：

- 填写：应对准带该字段含义的输入（标签、角色名），不是填进去之后的值，也不是通用占位符「请输入」。
- 选择：应对准下拉/组合框本身，选项文字属于数据。
- 点击：应对准按钮或链接的业务名称。
- 检查文本 / 检查可见：断言对象按目标定位，期望值只来自用例数据，不能把当前页面行为定义成正确答案。

没有书面合同之前，无法判断一次探索输出是对还是凑。

### 结构化输出

OpenCode 现在输出步骤顺序数组或 id 映射，字段是 `mode` / `text` / `role` / `selector`。缺口包括：

- 没有强制「定位文本应对齐目标，数据另存」。
- 宿主可用顺序硬对步骤，步骤错位也会显得「都有定位器」。
- 复用档案时 **不是** OpenCode 读档案再结构化，是宿主按键粘贴。档案不完整要增量探索时，才需要把档案当上下文再交给模型；这条路径目前很弱。

规格原意：OpenCode 只产候选；系统做 schema、定位器验证、正式写入。候选格式和宿主验收必须一起设计，不能只改模型说话方式。

### 页面档案复用

要回答：除了 `动作:目标` 键还要什么才算覆盖？错定位器如何作废、刷新、不污染下一案？增量补探和整页重探怎么选？失败结果继续禁止合入档案。

### 页面状态与一次探索的范围

弹窗、树、表格是否拆成不同页面状态？一次会话按用例跑完，还是按页面/状态切开？范围过大会超时，切太碎会丢「打开弹窗后才能填」的先后关系。

### 不完整结果

缺步骤、定位器对不上目标时，用户应看到失败或待确认，而不是一个能点发布的错误选择器。探索不完整时的降级是后续能力；当前先保证：完整结果是对的，不完整就不要假装完整。

## 讨论时建议先定的问题

1. 填写 / 选择 / 点击 / 断言的定位器合同（正反例）。
2. 合同由提示约束、宿主校验，还是探索过程中用 MCP 再验证一次？校验失败是探索失败、待确认，还是禁止写入档案并重探？
3. 页面档案的覆盖条件，以及错事实的作废方式。
4. 弹窗 / 树 / 表格要不要成为独立页面状态。
5. 一次探索的范围和超时策略。
6. 不完整结果的用户可见出口（失败、待确认、可单条重试）。

#19 正式客户端打包与最终验收仍依赖这条真实探索质量，不在探索重构完成前关闭。
